# Private content encryption

Backend-managed encryption now covers private database fields across accounts, documents/pages, health, family/trust, wealth, integrations, temporary records, generated packages and jobs. Operator endpoints expose public catalogue definitions or operational counts, never user content. Production schema/backfills and all 30 constraints were verified under maintenance on 2026-10-16; application deployment and smoke-test evidence are recorded separately from source checks. A manual production recovery archive and isolated restore tests are verified, and direct Data API access hardening has been applied; see [the executed recovery/security checkpoint](manual-production-backup.md).

**Boundary:** anyone controlling the backend and its keys can decrypt content. This is not zero-knowledge and does not prevent a server operator with backend/key access from reading data. Operator API redaction and database encryption are separate controls. Preventing backend decryption would require client-held keys: AI would need client processing or explicit plaintext disclosure, recovery would need user-held recovery material, search would move to clients or constrained searchable indexes, and sharing would require recipient key wrapping/revocation. This implementation retains server-managed keys.

## Coverage

The complete, model-by-model [field matrix and readable allowlist](field-inventory.md) is derived from Prisma and `src/privacy/operationalFields.ts`. The [persistence/I/O index](persistence-paths.md) records inspected paths. Private fields default to protected; adding a Prisma model requires classification, and protected scalars require a corresponding ciphertext column.

| Area | Protected primary and duplicate/derived copies | Behavior preserved |
|---|---|---|
| Accounts/authentication | Names, email, country/passport/currency/preferences; pending signup/account-change details; Google account identifiers/avatar | Restricted exact credential discovery; password/PIN/OTP/OAuth/token verification precedes profile decryption. JWTs contain opaque subject/auth version only. |
| Documents/pages/identity | Names/titles, classifications, extracted text/JSON, document numbers, fingerprints/original hashes, provider IDs, source dates/checksums, locators and wrapped keys; identity profile copies and verification outcomes | Manual/bulk/nested writes, analysis, matching, search, page ordering and storage quota deduplication. Existing encrypted file bytes remain encrypted. |
| Health | Member identity/contact/insurance, extracted/pending JSON, measurements, metric identifiers/ranges/units, clinical dates, medication fields/statuses, schedules/repeat/completion flags, follow-ups/reminders | Typed numbers/dates/booleans restored after authorization; clinical filtering/sorting/reminders run on authorized decoded values. |
| Family/trust | Name/email/relationship/DOB/blood group; duplicated health-member details | Token/PIN-gated acceptance, revocation and module permissions; linked owner projection restricted to id/name/email. Unverified invitation previews are generic. Wealth handoff requires view and download permission before building content. |
| Wealth | Type/title/details/amount-bearing JSON/notes/follow-up dates and notes; linked documents | Authorized CRUD/filtering, exports and permission-checked handoff. |
| Integrations/temp/push | OAuth refresh tokens/account emails/scopes, candidate sender/subject/filename/date/classification/signals/reasons, external identities, temporary names/digests/wrapped keys, consent URLs/documents/messages, push endpoint/keys/user agent | Existing integration records remain encrypted; Gmail/Drive routes are disabled for future work. Temporary uploads, keyed uniqueness and provider credential readers are retained. |
| Jobs/generated packages | Package request/labels/draft/messages/errors/confidence/disclaimer/dedupe; user-specific package title/slug/requirements/metadata/search copies | Queue polling/retries/leases; encrypted owner-scoped generated catalogue. Public seed metadata no longer accumulates user searches. |
| Export/cleanup | ZIP bytes and export error text; cleanup object locator | Authorized download decrypts in memory; encrypted export object at rest; cleanup uses keyed locators and byte accounting. |

Readable fields are limited to opaque relationships, created/updated timestamps, processing/access lifecycle, retry/lease/revocation state, byte sizes/MIME/encryption descriptors, account plans/quotas, sharing permissions and public operator-authored definitions. Reasons and exact fields are in the matrix. Medical dates/states/measurements, identity details and financial types/values are excluded. Authentication password/PIN/OTP/token hashes remain restricted one-way verifiers, never operator DTO fields. Random OAuth state tokens are replay-prevention capabilities. Existing opaque encrypted-temp/export locators and fixed server-generated export filenames are storage routing metadata; operator projections omit storage capabilities and cryptographic internals.

## Storage and authorization design

`authenticatedEncryption.ts` provides shared AES-256-GCM primitives. Versioned `enc:v2:<key-id>:<nonce>:<tag>:<ciphertext>` envelopes use fresh 96-bit nonces, 128-bit tags, per-model/field HKDF keys, and authenticated version/key/model/record/owner/field binding. Keys are external configuration, never database columns or logs. Independent HMAC keys support exact lookup/uniqueness. Lookup namespaces are owner-specific except global authentication/email linking/provider identity and push-endpoint uniqueness. Equality within an index scope remains visible; lookup-key rotation needs an index-transition migration.

The Prisma facade preserves application-facing field types and API shapes. Dedicated `private_*` text columns store ciphertext; original columns contain keyed lookup tokens or fixed null/empty/zero sentinels, including encrypted original nulls. Nullable lookup fields retain SQL NULL-distinct uniqueness; their original null is also encrypted. There are no readable shadow copies. SQL CHECK constraints reject accidental plaintext, including raw/nested/bulk writes. Composite foreign keys bind document pages and requirement provenance to their parents. Constraints check representation; AEAD readers authenticate actual content. A database administrator who can disable constraints is outside this enforcement boundary.

AsyncLocalStorage grants explicit authenticated owner capabilities. Private fields are decrypted only when requested/predicated/sorted inside that scope. Restricted credential projections do not decrypt profiles. Offline migration capabilities are not HTTP admin capabilities. Linked trust membership permits only the existing shared membership/profile projection; handoff paths check current module permissions. Admin package queries restrict to public seed definitions. Notification delivery returns counts and account deletion returns processed counts. Admin tokens are required in every environment.

Private range/substring/array/JSON predicates and sorting run after authorization; exact string predicates can use keyed SQL candidates. Original concurrency/status/lease predicates remain on writes, and private predicate updates compare observed ciphertext. Interactive transactions and nested creates stay protected. Unsupported private aggregate/update operators fail closed. Application processing can scan an owner's candidate set and has a CPU/memory cost; benchmark large accounts before rollout. No plaintext durable search/cache indexes are created. Public catalogue categories alone are cached across users; in-flight refresh work is scoped to an accessible package.

Diagnostics omit file names, extracted values and provider/database exception text. Prisma parameter logging is disabled; HTTP errors retain safe codes and generic messages. Authenticated responses use `private, no-store`. Durable temporary upload objects and ZIPs are encrypted. File validation and AI preparation require transient plaintext memory and restricted scratch files (0700 directories/0600 files), with finally cleanup; process crashes can leave scratch files. Before rollout, inventory/clean stale worker scratch directories while all workers are stopped. Use isolated ephemeral worker storage and retain the startup upload cleanup; this is not protection against a running backend or host administrator. JS strings cannot be reliably zeroized. Authorized handoff email/download content and explicitly enabled AI/provider processing remain intentional disclosures.

## Coordinated rollout (do not run in production as part of this task)

1. Back up database and storage using controlled procedures. Inventory object versions, backups, old plaintext exports and stale scratch files without printing private names/content. Database rewrites do not erase old WAL/snapshots/backups or provider object versions. Restrict those copies and expire/delete them under the existing retention policy. Retain all legacy document/RSA/OAuth keys needed to decrypt existing ciphertext; migration wraps legacy encrypted values without discarding keys.
2. Provision `PRIVATE_DATA_KEYRING_JSON` (JSON object of key IDs to `base64:` plus 32 random bytes encoded as base64), `PRIVATE_DATA_ACTIVE_KEY_ID`, and a **different**, stable `PRIVATE_DATA_LOOKUP_KEY` in the same format. Use a secret manager; never SQL, source, command arguments or logs. `DOCUMENT_ENCRYPTION_KEY` is now mandatory even in development; preserve its original value. Legacy passphrase decoding remains for existing v1 compatibility, while v2 keys strictly require 32 bytes. If historical development records used the old hardcoded fallback, configure its exact derived legacy key externally for recovery before migrating; there is no silent runtime fallback. Keep original RSA/OAuth keys externally configured too.
3. Stop **all** old API instances, cron invocations, import workers, queue processors, export/download handlers and writers. Keep them stopped through verification. This is a maintenance rollout, not a rolling deployment: new readers reject legacy plaintext and NOT VALID constraints already apply to new/updated rows. Prevent automatic deployment migrations from running ahead of this maintenance window.
4. Apply the original nine migrations `20261015190000` through `20261015235000`, followed by `20261016120000_private_health_extraction_outcomes` in repository order using the normal Prisma migration process; generate Prisma Client. Do not use `prisma db push` on an existing/shared database. Columns are additive; constraints are initially NOT VALID to preserve legacy records for the controlled backfill.
5. In the intended database/storage/secret environment, run these **in order**. The first command of each group is a counts-only dry-run; `--verify` authenticates ciphertext, checks masks/pending work and returns nonzero on incomplete migration. Reports omit IDs, values and object paths.

   ```sh
   npm run privacy:migrate-records
   npm run privacy:migrate-records -- --apply
   npm run privacy:migrate-records -- --verify
   npm run privacy:migrate-jobs-exports
   npm run privacy:migrate-jobs-exports -- --apply
   npm run privacy:migrate-jobs-exports -- --verify
   ```

6. Backfills use keyset batches (100 records/jobs, 20 exports); records are reread under locks and each successful row is its checkpoint. Restart the same command after interruption. Valid ciphertext is authenticated and left intact; mixed rows resume; corrupt/unknown-key ciphertext stops the migration. Database IDs/relationships are preserved except historical private requirement IDs containing content, which are replaced with UUIDs and cascaded to assignments. Reload clients holding old cached requirement IDs.
7. Historical global `createdBy=ai` package rows lack reliable ownership: they are preserved encrypted under a quarantined owner and excluded from user/admin queries. Do not guess owners. Old public seed aliases/keywords/search/provenance metadata may contain search inputs: the original values are archived in bound ciphertext (`legacyPrivateMetadata`), visible copies cleared and verification reset for review. Reimport/review public source metadata from trusted definitions to restore catalogue discovery/verification. Seed title/description/requirements are operator-authored public definitions. Orphan document records remain preserved and inaccessible until ownership is resolved offline.
8. Export migration handles every referenced archive, including non-READY jobs. ZIPs upload to a new encrypted object, then the database pointer and encrypted cleanup queue commit together. Verify `cleanupPending=0`; deletion failures are retryable. An interrupted upload before pointer commit can leave a ciphertext orphan for storage reconciliation. Missing referenced objects or unsupported legacy formats fail closed and require offline reconciliation; the script does not invent replacement data. It does not inspect unreferenced/provider-versioned objects.
9. After **both** verification commands pass, execute [validate-constraints.sql](validate-constraints.sql) against that selected database. Reconcile pending counts and quarantine decisions before restarting new APIs/workers. Exercise signup/login/PIN/refresh, manual uploads, health/medication/reminder flows, custom packages, sharing revocation, quotas, exports and admin responses. Roll back only to encryption-capable readers retaining all keys; do not restore plaintext writers or drop guards to run old binaries.

Key rotation: keep old key IDs, switch the active encryption key for new writes, and perform a separately reviewed re-encryption backfill. These resumable scripts intentionally skip valid ciphertext and are not rotation tools. Never change the HMAC key without rebuilding/transitionally preserving all affected unique lookup indexes. Single-value/archive encryption is bounded at 512 MiB; larger exports require a streaming design.

## Validation

```sh
npm ci
npm run prisma:generate
npx tsc --noEmit
npm run test:privacy
```

Integration tests deliberately accept **only** `PRIVACY_TEST_DATABASE_URL` with host `127.0.0.1`, port `55439`, database `privacy_test`. Start a disposable PostgreSQL 17 container `readiness-privacy-test-d4e2` with that mapping and database, set the local-only test password/URL, initialize its schema with `prisma db push`, then run `npm run test:privacy:integration`. Never target a shared or production database: tests alter constraints to manufacture legacy fixtures. Each process provisions random synthetic keys and cleans its fixtures/storage; suites must run serially. Provider tests use mocks and make no Google/OpenAI/email/push requests. Stop/remove the container afterwards.

Recorded checks for this branch are in [local-validation.md](local-validation.md). The normal local database migration is recorded separately from disposable regression tests.

## AI extraction and future integrations

Standalone OCR, PDF text parsing, Office text extractors, rule classifiers, preprocessing workers and fallbacks are removed. Original PDFs and every image page go directly to OpenAI with provider storage disabled. Health uses the same original-file approach. AI-disabled accounts use manual entry; failures offer retry/manual entry. Failed/disabled health retries preserve previously stored clinical data. PDF structural validation, image validation, previews, encryption, page order and file preparation remain. Manual field definitions and validators moved to `src/services/documents`; legacy source labels and decryption readers remain for stored data.

Removed dependencies: `tesseract.js`, `@tesseract.js-data/eng`, `pdf-parse`, `mammoth`, `word-extractor`. `pdf-lib` now performs structural validation without text extraction. Gmail/Drive mounts and OpenAPI operations are commented out for future work; their saved records and migration coverage remain.
